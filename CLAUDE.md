# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

WhatsApp chatbot (via **YCloud**, an official Meta BSP — chosen specifically to avoid the raw Meta Cloud API and unofficial/unsafe WhatsApp libraries) with Claude for AI, managing the appointment schedule of a dental clinic with multiple dentists. **Directus** (self-hosted, Docker, Postgres) is the system of record for all data and doubles as the admin panel for dentists/reception. See [`PLAN.md`](./PLAN.md) for the full phased plan and [`README.md`](./README.md) for current status/setup.

This repo actually contains **three independently-built projects**:
1. The main Node/TS application (root `package.json`) — the WhatsApp webhook, AI layer, and scheduling engine. Deployed as a Docker container (`clinica-dental-bot`) on the droplet.
2. `directus-extensions/appointments-overlap-guard/` — a **separate** Directus hook extension with its own `package.json`/`node_modules`/build, deployed independently onto the Directus Docker host. It is not part of the main app's build or dependency tree.
3. `clinica/` — a **separate** Vue 3 + TypeScript SPA (its own `package.json`/`node_modules`/build) for reception/dentists: login, dashboard stats, manual appointment CRUD, per-dentist agenda view, a patients-record maintenance screen (reception + admin; soft-delete only, admin-only), and a reception-only "Mensajes" screen that drafts the confirmation/recall texts reception sends by hand while the WABA is locked (see `clinica/README.md`). No backend of its own — talks directly to Directus's REST API, authenticated via Directus's own login (session cookie), so each user's permissions are whatever their Directus role/policy grants. Deployed as static files (not Docker) at `https://panel.egonia.site`. See [`clinica/README.md`](./clinica/README.md).


Run a single test file:
```bash

```

Administrative scripts (require `DIRECTUS_ADMIN_TOKEN` — a full-permission token, distinct from the app's restricted `DIRECTUS_TOKEN`):
```bash
DIRECTUS_ADMIN_TOKEN=<admin_token> npm run provision   # create/update Directus collections (idempotent)
DIRECTUS_ADMIN_TOKEN=<admin_token> npm run seed        # load doctors/services/working_hours (idempotent; edit CONFIG block in scripts/seed-directus.ts first)
DIRECTUS_ADMIN_TOKEN=<admin_token> npm run provision:passwords -- --fix-permissions   # password module: must_change_password field + read/update permissions (idempotent)

```

Three more provisioning scripts have no `package.json` alias and are run with `npx tsx`: `scripts/provision-clinics.ts` (multi-tenant schema), `scripts/provision-clinic-permissions.ts` (per-clinic policy filters) and `scripts/provision-cancellation-fields.ts` (los tres campos de trazabilidad de la cancelación en `appointments`). Full order on a fresh instance: `provision` → `provision-clinics.ts` → `provision-doctor-clinics.ts` → `provision-cancellation-fields.ts` → `provision-clinic-permissions.ts` → `seed`.

`scripts/shorten-booking-links.ts` is run the same way but isn't provisioning: it calls Short.io (`SHORTIO_API_KEY`, `SHORTIO_DOMAIN`, optional `PANEL_BASE_URL`) to shorten each clinic's `.../agendar?clinica=<uuid>` and stores the result in `clinics.booking_short_url`, which is what the panel's Mensajes screen pastes into the cancellation text ("Agende su cita aquí: …"). Supports `--dry-run` and `--force`. **A clinic that already has a link is skipped on purpose** — regenerating it would break the links already sitting in patients' phones. It stays useful as a manual backfill/retry tool even though clinic creation now generates the link automatically (see `clinic-booking-link-hook` below) — e.g. if Short.io was down when a clinic was created, or for clinics that predate the hook.

Directus extensions (each one a separate install/build — `appointments-overlap-guard`, `waitlist-notify-hook`, `time-off-cascade-hook`, `force-password-change-hook`, `appointment-cancel-stamp-hook`, `working-hours-guard`, `clinic-booking-link-hook`):

## Architecture

### Data layer: Directus, not an app-owned ORM
There is no Prisma/TypeORM — Directus itself is the database layer, API, and admin UI. `src/directus.ts` defines the `Schema` (one interface per collection: `ClinicRow`, `SpecialtyRow`, `DoctorRow`, `ClinicDoctorRow`, `ServiceRow`, `WorkingHoursRow`, `TimeOffRow`, `PatientRow`, `AppointmentRow`, `MessageRow`, `WaitlistRow` — note the collection is `doctors`, not `dentists`; older notes in this file still use the pre-rename names) and exports a typed `@directus/sdk` client (`directus`) authenticated with `DIRECTUS_TOKEN` (the bot's restricted service-account token, not admin). All reads/writes from the app go through this client — see `src/repositories/*.ts` for the read/write helpers (e.g. `findOrCreatePatient`, `logMessage`).

Collections are created/updated via `scripts/provision-directus.ts` (schema) and populated via `scripts/seed-directus.ts` (data), both idempotent and run manually against the live Directus instance — there are no migration files.

**`@directus/sdk` typing gap for date-range filters:** the SDK only types `_gte`/`_lte`/`_gt`/`_lt` filter operators as available when a `Schema` field is branded with the literal type `'datetime'` (via its internal `FieldOutputMap`) — but that same branding breaks `createItem`/`updateItem` payloads, which type against the raw `Schema` field (so they'd expect the literal string `"datetime"`, not an actual ISO string). This is an acknowledged SDK limitation (their own source has a `// TODO would love to filter this based on field type but thats not accurate enough in the schema atm`), not something fixable in this codebase. Two different workarounds are used depending on the caller:
- Bot (`src/repositories/*.ts`): keeps date fields as plain `string`, and simply doesn't filter by date range at the Directus-query level — fetches all rows for a dentist (filtered only by `dentist`/`estado`) and lets the pure domain logic (`hasOverlap`/`computeAvailableSlots`) ignore whatever doesn't overlap. Fine at this scale (small clinic).
- Vue panel (`clinica/src/lib/queryHelpers.ts`, `dateRangeFilter()`): casts the filter value `as never` (which is assignable to anything) to bypass the check at the call site, since the panel's dashboard genuinely needs server-side date-range filtering (stats queries) rather than fetching the whole table.

### Scheduling engine is pure and Directus-agnostic
`src/domain/availability.ts` (`computeAvailableSlots`, `hasOverlap`) takes plain JS data (services, working hours, time off, existing appointments) and returns available slots — it does not import Directus or touch the network. All duration/buffer/overlap/past-time business logic lives and is tested here (`availability.test.ts`) independent of any I/O. `src/repositories/availability.ts` and `appointments.ts` wire it up against real Directus data (see "AI layer" below and their own test files).

### Double-booking integrity is enforced twice, independently
1. In Node, via `hasOverlap` before writing — wired into `bookAppointment`/`rescheduleAppointment` in `src/repositories/appointments.ts`, used by both the AI tool layer and (transitively) anything that imports those functions.
2. In Directus itself, via the `appointments-overlap-guard` hook extension, which rejects (HTTP 403, `@directus/errors` `ForbiddenError`, message contains "solapa") any create/update on `appointments` that overlaps another active appointment for the same dentist, honoring the service's `buffer_min`. This applies regardless of the writer (bot, Vue panel, or any other API client) — the whole point of enforcing it at this layer too. **Directus hook context in this version does not expose the old `context.exceptions` pattern** — throw errors from the `@directus/errors` package instead (it gets bundled into the extension's build correctly; there is no host-injected exceptions object to destructure). `bookAppointment`/`rescheduleAppointment` catch this 403 (via `isDirectusError` + checking `extensions.code === "FORBIDDEN"`) and re-throw as the domain-level `SlotUnavailableError`.

### Time off cascades onto appointments (`time-off-cascade-hook`)
The check between `time_off` and `appointments` used to be one-directional: booking over an absence was blocked, but declaring an absence over already-booked appointments was not checked at all, leaving patients showing up to a consultation nobody would attend. Registering (or widening) an absence now cancels the appointments that fall inside it — `pendiente`/`confirmada` with a *future* `inicio` only; `completada` is never rewritten, and an absence entered retroactively doesn't touch appointments that already happened.

Enforced in two places, deliberately redundant and idempotent (whichever runs first, the other finds nothing left to cancel):
1. `directus-extensions/time-off-cascade-hook/` — a **third** hook extension (separate install/build/deploy, same as the other two). Unlike `appointments-overlap-guard` (a `filter`, which *rejects* writes), this is an `action`: it runs after the absence is written and mutates other rows, so it must not and cannot block. It builds its `ItemsService` with **`accountability: null`** (system access) — a dentist may register their own absence without having write permission on every affected appointment (the `Doctor` policy scopes appointments by `doctor.usuario`), and the cascade has to complete anyway. Events are left on in the `updateMany` so `waitlist-notify-hook` still fires (cancelling frees slots the waitlist can use); there's no recursion with the overlap guard, since `cancelada` isn't a blocking status and its filter returns early.
2. The Vue panel (`clinica/src/components/TimeOffFormModal.vue`) — queries the affected appointments *before* writing and requires explicit confirmation showing who is affected, then saves the absence and cancels them. Saving the absence comes first on purpose: the reverse order would leave appointments cancelled with nothing on record explaining why. The panel doesn't depend on the extension being deployed; the extension covers every writer that isn't the panel (Directus admin, API).

Cancelled appointments are flagged `cancelada_por_ausencia: true` — that's what separates them from a cancellation reception already agreed with the patient over the phone, and it's what feeds the "Cancelaciones" tab of the panel's Mensajes screen (`cancelacion_mensaje_enviado` tracks whether the patient has been told, same pattern as the other manual-send flags).

### Working hours: no overlaps, and shrinking one cascades onto appointments (`working-hours-guard`)
`working_hours` had no server-side rule at all: the same doctor could hold Mon 08:00–11:00 and Mon 10:00–12:00 (duplicated slots reaching the availability engine and the occupancy report), and deleting or trimming a block left the appointments booked in it untouched — the patient shows up to a consultation nobody will attend, the same gap `time-off-cascade-hook` closed for absences.

Two rules, both enforced in the panel (`AddWorkingHoursModal.vue` / `WorkingHoursView.vue`) *and* in the `working-hours-guard` extension, redundant and idempotent for the same reason as time off:
1. **No overlapping blocks, CROSS-CLINIC.** A doctor can't be in two places at once, so the check ignores `clinic` — exactly like `appointments-overlap-guard`, and for the same reason its `working_hours` service is built with `accountability: null` (a receptionist at clinic A can't read the block at clinic B, so the clash query would come back empty). Adjacent blocks (08–11 + 11–13) are fine: intervals are half-open. The panel can only check its own clinic, so a cross-clinic clash surfaces as the hook's 403 — mapped in `directusErrors.ts` by the word **"superpone"**, checked *before* the "solapa" branch that belongs to the appointment guard.
2. **Losing hours cancels the appointments that fall in them.** Affected = *overlaps the slice that disappears*, computed as `union(day's blocks before) − union(day's blocks after)`, not "everything outside the new schedule": an appointment booked out-of-hours was already out-of-hours and this change didn't break it. The union (rather than a block-by-block diff) is what makes deleting one of two blocks on the same day only cancel what no remaining block covers. Pure and tested in `clinica/src/lib/workingHours.ts` (+ `.test.ts`); the extension duplicates that logic locally, as extensions never import from the repo root.

Cancellations reuse `cancelada_por_ausencia: true` with `motivo_cancelacion: "Cambio de horario del médico"` — no new field, so the Mensajes screen and the Cancellations report pick them up unchanged; `buildCancellationMessage` was generalised to "un cambio imprevisto en la agenda del profesional", which covers both causes.

Two things worth not re-deriving:
- **The cascade needs a `filter` *and* an `action`.** An `action` runs after the write, when the previous schedule no longer exists and there's nothing to diff against; so the `filter` snapshots the doctor+clinic's blocks into a module-level `Map` and the `action` diffs it against the stored state. It has to stay an `action` (it mutates other rows and must not be able to abort the schedule write), same call as `time-off-cascade-hook`. The `action` drains *every* pending snapshot, because on a delete the row is gone and the pair can't be re-derived; evaluating one extra snapshot is harmless (nothing missing → nothing cancelled), and stale entries are purged after 30s.
- **The extension needs the clinic's timezone** (`CLINIC_TIMEZONE` env, default `America/Costa_Rica`): `hora_inicio`/`hora_fin` are zoneless `time` columns while `appointments.inicio` is a `timestamp`, so deciding which weekday/minute an appointment falls on requires it. It resolves that with `Intl.DateTimeFormat` rather than pulling in Luxon.

### A doctor can work at several clinics (`clinics_doctors`)
`doctors.clinic` used to be an M2O: one doctor, one clinic. A dentist who works Mon–Wed at clinic A and Thu–Fri at clinic B could not be represented at all. Now **one `doctors` row = one person**, and the clinics they work at live in the M2M junction `clinics_doctors` (`clinics_id`, `doctors_id`, plus the two things that depend on the clinic: `specialty` — `specialties` is itself clinic-scoped — and `activo`, so a doctor can be deactivated at one clinic without touching the others). The effective "does this doctor work here" rule is `doctors.activo && clinics_doctors.activo`. `working_hours` and `time_off` gained their own `clinic` field (they used to be derived through `doctor.clinic`, which no longer identifies anything).

**Keeping a single `doctors.id` per person is the whole point of the M2M**, and the reason the alternative (one `doctors` row per clinic, sharing a Directus user) was rejected: `hasOverlap`, `bookAppointment`/`rescheduleAppointment` and the `appointments-overlap-guard` hook all key off `doctor`, so with one identity they keep blocking a booking at 10:00 in clinic B when the doctor already has one at 10:00 in clinic A. Two rows would be two ids and nothing would stop it.

Which reads are clinic-scoped and which are deliberately not:
- **Appointments: cross-clinic on purpose.** A doctor cannot be in two places at once, so a booking anywhere blocks the slot everywhere. `blockingAppointmentsForDoctor` (`src/repositories/appointments.ts`) and the availability engine's appointment read (`src/repositories/availability.ts`) carry no `clinic` filter, and both have a comment saying so — don't "fix" it.
- **Working hours and time off: per clinic.** Different days at each site, and an absence blocks only the site where it was filed (a deliberate product decision — vacation entered at clinic A still leaves the doctor bookable at B; a "apply to all my clinics" checkbox in `TimeOffFormModal` is the obvious follow-up).

Two consequences worth knowing:
1. **`appointments-overlap-guard` must build its `appointmentsService` with `accountability: null`.** With the user's accountability, a receptionist at clinic A cannot read the doctor's appointment at clinic B, the clash query comes back empty and the cross-clinic double booking goes through. Same reasoning as `time-off-cascade-hook`. The other two services in that hook keep the user's accountability (they only read within the clinic).
2. **The panel's client-side slot calculation can offer a slot the server then rejects** (403 "se solapa"), because permissions only let it see the current clinic's appointments. That's the only option that doesn't leak another tenant's data; the guard's error message deliberately doesn't say where the conflicting appointment is.

Permission filters (all in `scripts/provision-clinic-permissions.ts`): `Receptionist` reaches `doctors` through the junction (`{clinicas: {clinics_id: <RECEPTIONIST_CLINIC_CONDITION>}}`, deliberately *not* requiring `activo` — reception must still see a deactivated doctor), and `working_hours`/`time_off` now filter on their own `clinic` instead of `doctor.clinic`. `Doctor`'s `clinics.read` uses `DOCTOR_CLINIC_CONDITION` (`{medicos: {doctors_id: {usuario: $CURRENT_USER}, activo: true}}`) — that's what makes the panel's existing clinic selector appear for a multi-clinic doctor. Everything keyed off `doctor.usuario` (`appointments`, `working_hours`, `time_off`) is unchanged, since `doctors.usuario` doesn't depend on the clinic. **The bot's policy needs `clinics_doctors.read`** or `listActiveDoctors` returns nothing and it can't book at all.

Migration is `scripts/provision-doctor-clinics.ts`, idempotent and phased so there's no downtime: no flags = additive schema (all nullable) + backfill from `doctors.clinic`/`doctors.specialty`; `--dry-run` = counts only; `--finalize` = verify zero nulls (aborts with an explicit message otherwise), NOT NULL on the new columns, and loosen the old ones — **run this before deploying the new code**, which no longer writes them; then deploy bot + the two rebuilt extensions + panel and re-run `provision-clinic-permissions.ts`; `--drop-legacy` days later removes `doctors.clinic`, `doctors.specialty` and the orphan `clinics.doctores` alias. Everything before `--drop-legacy` is reversible by redeploying the previous code. Unique `(clinics_id, doctors_id)` is enforced by the script checking before insert — Directus's field API has no composite index, so harden it by hand in psql if it matters.

### AI layer (Claude + tool use)
`src/ai/`: `tools.ts` defines 8 tools for Claude (`list_services`, `list_dentists`, `check_availability`, `book_appointment`, `get_my_appointments`, `reschedule_appointment`, `cancel_appointment`, `handoff_to_human`), each a thin wrapper around the repositories in `src/repositories/`. `agent.ts` runs the tool-use loop against the Anthropic SDK (`@anthropic-ai/sdk`), capped at `MAX_TOOL_ITERATIONS = 6`. `systemPrompt.ts` is regenerated every turn (so "now" stays accurate for resolving "mañana"/"el viernes") and encodes the core policy: never invent availability (always call `check_availability` first), always get explicit confirmation before booking/rescheduling/cancelling, and use WhatsApp's own bold syntax (`*text*`, single asterisk) not Markdown's `**text**`.

Business-rule failures (e.g. `SlotUnavailableError`) are caught inside each tool handler and returned as `{ error: "..." }` — a normal tool result the model can react to — rather than thrown; unexpected errors propagate up to `agent.ts`'s loop, which reports them to Claude as an `is_error` tool result and logs via `console.error`.

**Ownership check on cancel/reschedule (found in a manual security review, fixed):** the bot's `DIRECTUS_TOKEN` has broad CRU permissions across *all* appointments (it must be able to serve any patient), so Directus itself won't stop one patient from cancelling/rescheduling another's appointment by id — that check has to live in application code. `cancelAppointment`/`rescheduleAppointment` in `src/repositories/appointments.ts` take a `patientId` and look up the row via `getOwnAppointmentRow()` first, throwing `AppointmentNotFoundError` (caught in `tools.ts` and returned as a normal `{error}` tool result, same pattern as `SlotUnavailableError`) if the appointment doesn't exist or belongs to someone else.

### WhatsApp integration (YCloud)
`src/whatsapp/`:
- `ycloud.ts` — outbound send client (`sendText`, `sendButtons`, `sendList`) against `POST https://api.ycloud.com/v2/whatsapp/messages/sendDirectly`, auth via `X-API-Key`. **Note:** this only throws if the HTTP call itself fails (`!res.ok`); YCloud can return `200 {status: "accepted"}` and still fail to actually deliver the message (e.g. a locked WABA) — that only surfaces later via `GET /v2/whatsapp/messages/{id}` or the `whatsapp.message.updated` webhook event, neither of which this code currently checks.
- `signature.ts` — verifies the `YCloud-Signature: t=...,s=...` header (HMAC-SHA256 over `"{timestamp}.{rawBody}"`); requires the raw request body, so `server.ts` captures it via express.json's `verify` callback rather than re-serializing `req.body`. `t` is unix seconds (confirmed against YCloud's docs); also enforces a 5-minute freshness window (`TIMESTAMP_TOLERANCE_SECONDS`) so a captured valid request can't be replayed indefinitely — added in a manual security review, YCloud's own guide only covers the HMAC check, not replay protection.
- `types.ts` — shape of the `whatsapp.inbound_message.received` webhook event.

`src/server.ts` is the webhook entrypoint (`POST /webhook/ycloud`): rate-limited (`express-rate-limit`, 60 req/min, defense-in-depth against flood/cost-abuse — the HMAC signature is the real authentication), validates the signature (skipped if `YCLOUD_WEBHOOK_SECRET` is unset, e.g. in local dev before the YCloud account exists), acks 200 immediately, then processes the inbound message asynchronously — find-or-create patient, log message, build conversation history (`toConversation()` merges consecutive same-role messages, since Claude's API requires strict user/assistant alternation and a patient can send several WhatsApp messages before the bot replies to the first), invoke `runAgentTurn`, send the reply, log it. `app` and `processInboundEvent` are exported (not just `app.listen()`ed unconditionally) so tests can drive them without binding a real port — the `app.listen()` call is guarded by an `import.meta.url === pathToFileURL(process.argv[1]).href` check so it only fires when the file is run directly. `app.set("trust proxy", 1)` is required for the rate limiter to see the real client IP (and not throw) behind the single Nginx reverse-proxy hop on the same host.

The Docker image runs as the unprivileged `node` user (`node:22-slim` ships it built-in) instead of root — added in a manual security review, standard defense-in-depth for a container with no functional need for root.

### Reminder scheduler (WhatsApp templates)
Outside WhatsApp's 24h session window, only Meta-approved templates (HSM) can initiate contact — needed for appointment reminders since the business, not the patient, starts that conversation. `src/domain/reminders.ts` (`duesReminders`) is the pure, tested piece: given an appointment's `inicio` and its two boolean flags (`recordatorio_24h_enviado`/`recordatorio_2h_enviado` on the `appointments` collection), it decides which reminder(s) are due *now* — triggered by "window is open and flag still false", not by an exact time match, so it's robust to the scheduler being down/restarted (a long outage can return both kinds at once, and each still fires exactly once thanks to its flag). `src/repositories/reminders.ts` wires this to Directus (`findAppointmentsDueForReminder` fetches broadly — same "filter in Node" pattern as `appointments.ts` — then applies the pure logic) and to WhatsApp (`sendReminder` resolves patient/service/dentist, calls `sendTemplate` in `ycloud.ts`, logs the outbound message, and **only marks the flag if the send didn't throw** — same fire-and-forget trust level as the rest of the codebase, see the `ycloud.ts` note above; a thrown error is retried on the next pass instead of being swallowed). `src/scheduler.ts` (`startReminderScheduler`) polls via `setInterval` every `REMINDER_CHECK_INTERVAL_MINUTES`; it's started from `server.ts` only inside the `isMain` guard and only if `REMINDERS_ENABLED=true` (default `false` — enabling real sends in production is a deliberate, separate decision), so importing `app`/`processInboundEvent` in tests never starts it. The two templates (`recordatorio_cita_24h`, `recordatorio_cita_2h`, category `UTILITY`, language `es`) are created/submitted for Meta review via `scripts/create-whatsapp-templates.ts` (idempotent, same pattern as `provision-directus.ts`) — a real side effect against the live WABA, run manually, not automatically. No interactive buttons: a patient replying to a reminder is just a normal inbound WhatsApp message, already handled end-to-end by the existing AI agent/tools.

### Cancellation trace (`appointment-cancel-stamp-hook`)
Three fields on `appointments` feed the panel's Cancellations report: `cancelado_en`, `cancelado_por` (`paciente|recepcion|medico|clinica|admin`, mirrored as the `CancelledBy` type in `src/domain/types.ts` and in the panel's `Schema`) and `motivo_cancelacion`. Created by `scripts/provision-cancellation-fields.ts`, **deliberately without backfill** — that data doesn't exist anywhere for older rows (there's no `date_updated` and no revision history), and stamping today's date would fabricate an anticipation figure nobody could later tell apart from a real one. They stay `null` and the report shows "sin dato".

There are four ways to cancel an appointment (panel, bot, `time-off-cascade-hook`, Directus admin), so the safety net is a hook rather than a rule each writer must remember. `appointment-cancel-stamp-hook` is a **`filter`** on `appointments.items.update` (and `.create`): when `estado` becomes `cancelada` **and the row wasn't already cancelled**, it fills whatever the payload didn't set — `cancelado_en` = now, `cancelado_por` derived from `accountability` (null → `clinica`; `admin` flag → `admin`; role name via a cached `directus_roles` lookup → `medico`/`recepcion`/`paciente` for the bot). Explicit payload values always win.

Three things worth not re-deriving:
1. **`filter`, not `action`** — it lands in the *same* UPDATE as the status change. An `action` would be a second write that can fail on its own and leave cancelled appointments with no date, which is the exact gap the hook exists to close. (Opposite call to `force-password-change-hook`, which *had* to be an `action` because its field is deliberately not user-writable.)
2. **The "wasn't already cancelled" check is load-bearing.** Without it, any later save of a cancelled appointment (writing the reason afterwards, flipping `cancelacion_mensaje_enviado`) resends `estado: "cancelada"` and overwrites the original timestamp — the report's anticipation figure would rot silently.
3. **It depends on `appointments.update` carrying `fields: ["*"]`.** A filter runs *before* the payload is validated against the writer's field permissions, so injecting these three fields would 403 a normal user if they weren't in the whitelist. Noted in `provision-clinic-permissions.ts`'s header.

The panel and the bot write all three fields explicitly anyway (redundant on purpose, same reasoning as the time-off cascade): neither depends on the extension being deployed.

### Auto-generated booking short link (`clinic-booking-link-hook`)
Every clinic needs a short link (`clinics.booking_short_url`) for its public booking form — the panel's Mensajes screen pastes it into the cancellation text. Used to be a purely manual step (`scripts/shorten-booking-links.ts`, run by hand after creating a clinic); a new clinic silently had no link until someone remembered to run it. `clinic-booking-link-hook` is an **`action`** on `clinics.items.create` that calls Short.io itself and writes `booking_short_url` right after the clinic row is created.

**`action`, not `filter`:** generating the link is a network call to a third party that can fail or be slow, and that must never block or delay creating the clinic. On failure it just logs and leaves `booking_short_url` null — `scripts/shorten-booking-links.ts` still exists as the backfill/retry path (idempotent: skips any clinic that already has a link), so it's not a dead script now that the hook exists.

**Why the Short.io API key is safe to put in this hook but not in the panel:** the key can edit/delete any link on the domain, which is exactly why `scripts/shorten-booking-links.ts`'s header says it must stay a hand-run script rather than live in the panel — the panel bundle is public, any `VITE_*` is readable in devtools. This hook runs server-side inside the Directus container, so the key sits in the container's env (`SHORTIO_API_KEY`, `SHORTIO_DOMAIN`, optional `PANEL_BASE_URL`, same three vars the manual script uses) the same way `CLINIC_TIMEZONE` does for `working-hours-guard` — never shipped to a browser.

Writes with `accountability: null` (same reasoning as the other hooks in this file): whoever creates the clinic — normally an admin from the panel's onboarding wizard — may not have `booking_short_url` in their field whitelist, and the hook's write shouldn't depend on that.

### Reports section (panel)
`clinica/src/lib/reports/` + `/reportes` and `/reportes/:reportId`. Eight reports today, designed so the ninth costs one file: every report is a `ReportDefinition` (`types.ts`) and there is ONE generic view (`ReportView.vue`) plus ONE pair of exporters that never learn what report they're rendering. The enabling constraint is that **every `ReportSection` carries `columns` + `rows` even when it's drawn as a chart** — table, PDF and Excel all read the same structure. Adding a report = a file in `definitions/` + a line in `registry.ts`.

Decisions that are easy to accidentally undo:
- **An appointment's specialty is its SERVICE's**, not its doctor's — the service is what the patient asked for and, unlike the doctor's specialty (which lives in `clinics_doctors` and is per-clinic), it doesn't depend on where they're seen. Only occupancy uses the doctor's, because agenda hours come from `working_hours`, which has no service.
- **Every query filters `clinic` in code.** The `Doctor` policy intentionally does *not* scope `appointments` by clinic (the overlap guard has to be cross-clinic), so without it a multi-clinic doctor silently sees merged totals. `shared.ts`'s `baseAppointmentFilter` takes `clinicIds` as a required argument for that reason.
- **Occupancy clips appointments against available hours** so out-of-hours bookings can't push the percentage over 100%; the excess is reported separately as `minutosFueraDeHorario`. Pure and tested in `occupancy.ts`.
- **"New patient" is derived from appointments** (first-ever appointment falls in that month), not from a creation date — that field doesn't exist and couldn't be honestly backfilled. Pure and tested in `patientMix.ts`.
- **No revenue.** No price field exists anywhere; it would need `services.precio` *and* a per-appointment frozen amount, or raising a tariff would rewrite closed months.
- **Excel gets raw values with native cell formats** (`0.91` + `0%`, never the string `"91%"`) — the whole point of exporting is to sort/chart it. The PDF is the opposite: pre-formatted, landscape, and v1 embeds no charts (extension point documented at the bottom of `toPdf.ts`).
- `jspdf`/`exceljs` load via dynamic `import()`; they must stay out of the initial bundle.

The panel now has its own vitest suite (`cd clinica && npm test`). The root `vitest.config.ts` exists solely to exclude `clinica/**` from the bot's suite — the two resolve `@/` differently.

### Directus permissions model (Access Policies, not classic Roles)
This Directus version uses **Access Policies** as the actual permission containers; a **Role** (or a User directly) only has permissions if a Policy is *attached* to it via `directus_access` — creating a Policy with rules does not automatically grant anything until it's linked. When debugging "valid token but 403 on everything," check `GET /roles?limit=-1&fields=id,name,policies,users` (empty `policies` array = no policy attached to that role) and `GET /access/{id}` to see whether a given access row targets a `role` or a `user` directly. The three application-relevant policies/roles are `Bot WhatsApp` (service account used by `DIRECTUS_TOKEN`: CRU on `patients`/`appointments`/`messages`, read-only on `dentists`/`services`/`working_hours`/`time_off`), `Dentist` (panel role for dentists, scoped to their own agenda via a `dentist.usuario = $CURRENT_USER` filter — requires each `dentists` row's `usuario` field to point at that dentist's Directus user account; **create is deliberately not granted** — dentists can view/update their own agenda but not create new appointments, only Receptionist can), and `Receptionist` (broad CRUD across `patients`/`appointments`/`messages`/`services`/`time_off`/`working_hours`).

**Dentist policy scoping on `dentists`/`patients`/`messages` (found in a manual review, fixed):** these three had no row filter at all (`permissions: null`, i.e. every row) for the `Dentist` policy, even though `appointments`/`working_hours`/`time_off` were already correctly scoped — verified live with a throwaway test dentist/user that any dentist could read every other dentist's name+linked user id, every patient's PII (name/phone/document/notes) regardless of ever having an appointment with them, and full CRUD on every patient's WhatsApp message history (which the Vue panel doesn't even use anywhere). Fixed: `dentists` read now filters `{usuario: {_eq: "$CURRENT_USER"}}` (own row only); `patients` read now filters through a reverse-O2M alias field added to the collection — `{appointments: {dentist: {usuario: {_eq: "$CURRENT_USER"}}}}` (a dentist can only see patients they actually have an appointment with), and its create/update/delete permissions were removed (the panel never needs a dentist to create/edit/delete a patient record, only look one up when editing their own appointment); `messages`' 4 permission rows were removed outright for this policy. The reverse-O2M alias (`patients.appointments`, pointing back through the existing `appointments.patient` M2O) didn't exist before this fix — added via `POST /fields/patients` (alias/o2m field) + `PATCH /relations/appointments/patient` (`meta.one_field`) — needed so a permissions filter can dot-path from `patients` back through `appointments` to `dentist.usuario`. Verified with the same throwaway-account technique: a test dentist with one appointment to "patient A" could read patient A but not an unrelated "patient B".

**`create` on `messages` for `Receptionist` is deliberately unfiltered:** the "Mensajes" panel screen logs every manually-sent message as a `messages` row, so the policy needs `create` there (added by `scripts/provision-clinic-permissions.ts`). Unlike its `read`/`update`/`delete` siblings, it carries no row filter — in Directus a `create` doesn't evaluate `permissions` (the row doesn't exist yet) but `validation`, which can't resolve the `patient.clinic` relation. Same known limitation already accepted for `working_hours`, documented in that script's header. The gap doesn't expose data: `read` stays scoped, so a receptionist couldn't even read back a row she wrote against another clinic's patient.

**Bug pattern to check for when a permission row exists but still 403s on filtered queries:** a `permissions` row can have its row-level `filter` (e.g. `dentist.usuario = $CURRENT_USER`) correctly configured while its `fields` column is `null` instead of `["*"]` (or an explicit list). Plain reads/writes of individual fields can still appear to work in some contexts, but filtering *by* a field ("You don't have permission to access field X") or combining an `aggregate` with a `filter` reliably 403s under this misconfiguration — Directus's field-permission check is stricter for filter/aggregate contexts than for plain field selection. Found and fixed twice in this project (`Dentist` policy's `appointments`/`working_hours`/`time_off` read+write rows all had `fields: null`; `Receptionist` was missing `working_hours` permissions entirely). Diagnose via `GET /permissions?filter={"policy":{"name":{"_eq":"<PolicyName>"}}}&fields=id,collection,action,fields,permissions` (needs an admin token) — compare against sibling rows that work. Fix with `PATCH /permissions/{id}` `{"fields": ["*"]}`, or `POST /permissions` with `{policy, collection, action, fields: ["*"], permissions: null}` to add a missing action entirely.

**`patients.update` for `Receptionist` is the one content-collection permission that deliberately does NOT use `fields: ["*"]`.** It carries an explicit whitelist (`PATIENT_EDITABLE_FIELDS` in `scripts/provision-clinic-permissions.ts`) that omits `activo` — the patient's soft-delete flag — because "only the administrator can delete a patient" has to be enforced by Directus, not by hiding a button in the panel. `patients.delete` is revoked outright for that policy (the script's `removePermission()`): `appointments`/`messages`/`waitlist` all reference `patients` with `ON DELETE CASCADE`, so a real delete would silently take the patient's whole history with it; the panel only ever flips `activo`. The `fields: ["*"]` invariant exists to dodge the 403 bug in *filtered/aggregate reads*, so an explicit list on an `update` doesn't reintroduce it. Cost of this choice: **every new `patients` field must be added to that list** or reception silently can't edit it.

**The `fields: ["*"]` invariant above does NOT apply to `directus_users` — there it is a privilege escalation.** In a content collection the security boundary is the row filter, and `fields: ["*"]` only exists to dodge the 403 bug in filtered/aggregate queries. On `directus_users` the row filter (`id = $CURRENT_USER`) is trivial and *the field list is the boundary*: a row `{collection: "directus_users", action: "update", fields: ["*"]}` would let any user do `PATCH /users/me {"role": "<Administrator id>"}`. And since Directus **unions** the permissions of every applicable policy, adding that row doesn't restrict anything — it widens the whitelist Directus already injects. `scripts/provision-password-management.ts` (`--fix-permissions`) only ever writes explicit field lists (`password`/`first_name`/`last_name` for `update`) on this collection, never `["*"]`.

**Directus's documented `appAccessMinimalPermissions` built-in (free `read`+`update` on the user's own row for any policy with `app_access: true`) does NOT reliably apply on this instance/version (11.14)** — verified live with a throwaway test account: a `PATCH /users/me {"first_name": "..."}` with zero explicit permission rows on `directus_users` returned a plain 403. Don't trust that built-in; `scripts/provision-password-management.ts --fix-permissions` writes the `read` and `update` rows explicitly instead of assuming they exist. This is why the `Doctor`/`Receptionist` policies needed explicit permission rows added on `directus_users` for the password module to work at all (permission ids `#161`/`#162` for `update`, existing rows `#74`/`#111` for `read` — the latter predated this feature and just needed `must_change_password` appended to their field list). Also found while doing this: this Directus instance already has a `requires_password_change` field on `directus_users`, unrelated to ours — it belongs to the `Client` policy, one of the unrelated products sharing this instance (see the PassKit/Google-OAuth note below). Don't confuse the two fields.

**Password management (panel):** `directus_users.must_change_password` (custom boolean field, created by `scripts/provision-password-management.ts`) traps a user in the panel's `/cambiar-clave` screen until they replace the temporary password the onboarding wizard or the admin's reset button gave them. The user deliberately **cannot write that field**; `directus-extensions/force-password-change-hook/` clears it — an `action("users.update")` that fires when the payload contains `password`, writing with `accountability: null` (the user has no permission on the field, so the write can't inherit their accountability) and `emitEvents: false` (no recursion; unlike `time-off-cascade-hook`, nothing downstream needs to hear about it). It returns early when the payload already sets `must_change_password` explicitly — that's what lets the admin's reset write `{password, must_change_password: true}` in one PATCH without the hook reverting it a moment later. A `filter` hook would be simpler and atomic, but it runs *before* the payload is validated against the user's field permissions, so a normal user's password change would 403. Full flow documented in `clinica/README.md` ("Contraseñas").
